# 多盘 M3U 方案、应用与恢复（阶段 2B）

实施日期：2026-11-16。依赖阶段 2A 的多盘与引用检查。本阶段不转换、移动或删除原光盘，不安装或更换核心。真实掌机运行、换盘和进度衔接仍待验收。

## 使用流程

1. 打开 Saturn／PlayStation 游戏列表，选择“多盘与引用检查”，展开至少包含两张盘的组，打开“编辑 M3U 方案”。
2. 勾选光盘并调整顺序，确认显示名称与 M3U 文件名。操作范围可以是“保存 M3U 并更新当前列表”，或“仅保存 M3U”。
3. “预览方案”展示实际 UTF-8 M3U 内容、目标地址、列表入口变化、存档与图片复制、其他列表引用、电脑备份位置及待处理问题。预览不写入设备文件；读取列表可能建立应用自己的持久标识。
4. 确认方案后，先退出 RetroArch，再点击“确认应用方案”。修改输入后必须重新预览；按钮不能重复提交同一个方案。
5. 在“设置 → 任务与恢复 → 多盘操作与恢复”查看记录、继续中断操作或恢复。恢复后重新读取当前游戏库；不要手工删除电脑备份。

“仅保存 M3U”不切换列表、不复制存档或图片、不建立新入口身份关联，也不联网核对核心；适用于配置尚不明确时先检查文件。已有相同内容且没有其他变化的方案不能再次应用。

## 文件与列表规则

- 按用户确认的顺序写相对路径，每行一个 CHD／CUE 入口。所有光盘与目标 M3U 必须位于同一卷；MTP 必须属于同一设备、同一存储。启动路径与传输路径使用阶段 1B 的明确映射，不能把 `mtp://` 当作 RetroArch 启动路径。
- 所选光盘须通过地区、修订／汉化标记、盘号、特殊盘、引用文件存在性等检查。已知缺盘、重复盘号或未解析描述格式阻止应用；未知总盘数仍明确提示人工核对。
- 不覆盖无关的不同内容 M3U，不忽略大小写冲突。可更新当前组已有的 M3U；另起文件名时保留旧 M3U。
- 更新当前 `.lpl` 时，仅把选中的光盘、其关联音轨入口及当前旧 M3U 入口替换为一个 M3U 入口，保留其他条目和列表字段。已有 M3U 中未选中的盘保留或补回独立入口。应用创建的组保存各盘原条目，后续拆分时恢复其人工名称和自定义字段；外部导入且没有原条目记录的 M3U，补回项使用盘文件名及当前组核心。
- 不更换单项核心；多个原入口核心不一致时不自动决定。切换列表必须核对官方 core-info 同时声明支持 M3U 与所选入口格式。官方声明不能证明当前安装版本、实际可运行或换盘成功。
- 引用覆盖限于当前列表同目录的 `.lpl`，读取失败会阻止列表切换。修改共享 M3U 的盘序也会影响其他引用它的列表，预览列出这些列表，但不改写它们。
- 只读取小型描述与配置（上限 1 MiB）、待复制的存档／已有图片（单文件上限 8 MiB）。CHD／BIN 等内容仅检查存在性和大小，不读取整盘、不验证内容等价或磁盘损坏。

## 存档衔接范围

M3U 文件名可能改变核心使用的存档基础名，不能只替换列表路径。

首版仅自动处理 Beetle Saturn 的 `.bkr/.bcr/.smpc`、Beetle PSX 系列的 `.srm/.0.mcr/.1.mcr`、PCSX ReARMed 的 `.srm`。配置必须可访问，并明确给出存档、即时存档及核心选项文件的绝对路径；自动配置覆盖和按游戏核心选项须明确关闭且保存。分目录、随内容存档、共享存档或未知规则会阻止自动切换，可选择仅保存 M3U。

按所选盘及原 M3U 基础名检查游戏内存档。多个来源内容不一致时，必须在“存档衔接选项”明确选择来源。已有目标存档若不同则不覆盖；只创建新基础名副本，保留全部原存档。编辑或改名已有 M3U 时也会检查该 M3U 当前使用的存档。

即时存档始终保留、不迁移、不声明与新入口或新盘序兼容。发现即时存档时须明确确认从游戏内存档继续；只有即时存档、没有已识别游戏内存档时阻止切换。检查通过仅表示文件与已实现规则符合，进度能否在实际核心载入仍需真机验证。

## 身份与图片

新 M3U 入口延续原主入口的 Game UUID，使用独立启动 Content UUID；原光盘和内容 UUID 留存在 `library-disc-groups.json`，不会删除旧标识绑定。记录包含原各盘条目、盘序和图片来源关联，避免重排、重新打开后丢失分盘信息。

已有人工图片选择保留，主入口选择延续到新入口。提供图片目录时，把已存在图片复制到新显示名称对应的图片路径，原图保留；不同目标图片不覆盖。该流程不联网下载新图片。未指定图片目录时明确提示尚未检查新入口的图片文件。

## 事务与恢复契约

`POST /api/m3u/preview` 返回异步任务，服务端保留实际方案。`POST /api/m3u/apply` 只接受一次性 `preview_job_id`，不采用客户端提交的写入路径或内容。输入变化、设备／列表变化和过期返回会使界面方案失效。

写入前检查源描述、列表、配置、图片／存档以及相关身份记录是否变化；存档目录快照能发现预览后新增的存档。创建 `<用户数据目录>/m3u-operations/<操作 ID>/`，先保存原文件、方案输出、元数据快照与 `manifest.json`，再逐项写入并回读校验。每个阶段记录真实完成状态。源光盘不纳入写入集，也不备份整个 ROM。

MTP 多文件操作不是原子事务。中断显示“部分完成”，不会误报成功。`GET /api/m3u/history` 与设置中的历史读取电脑记录；`POST /api/m3u/recover` 只接受操作 ID 与 `resume/restore`。

- 继续前复核原依赖及每个目标；已校验完成的步骤不会重复写入。
- 恢复列表及旧 M3U 内容，撤销本次新增且未发生变化的 M3U、存档副本和图片副本。原光盘、原存档、原图始终保留。
- 应用索引按本操作涉及的键恢复，保留其他任务后来新增的无关记录；必要时留下空索引容器，不整文件回滚覆盖其他工作。
- 中断于 MTP 替换目标改名、原目标暂时缺失时，可依据持久步骤及电脑备份恢复；受控测试覆盖这一情况。
- 备份损坏、目标被外部改动或相关身份字段变化时停止自动覆盖，显示“恢复待处理”及电脑备份目录，需核对后处理。没有无条件强制覆盖入口。

## 验证与待验收

本轮完整回归 346 项通过（含两个视口的真实浏览器流程）；M3U Node 状态测试 6 项通过；JavaScript 语法检查通过（14 个脚本、83 个事件处理器）。仅有环境现存的 urllib3／LibreSSL 警告。

自动检查覆盖：只读预览、单次方案消费、修改输入与过期响应、盘序、缺盘边界、保存冲突与显式来源、即时存档、M3U 改名存档衔接、原条目字段、身份与图片选择延续、已存在图片复制、拆分未选盘、空变化、源文件变化、部分失败、继续与恢复、备份损坏、MTP 替换中断、无关元数据保留。

真实浏览器在 1100×700 和 1440×900 的临时本地服务中，完成调整盘序、预览、应用、刷新为唯一多盘入口、从设置恢复原列表与计数，并核对浅色与深色界面。测试样例不代表实际 CHD 可加载。

本轮不重启日常 7777 服务、不访问或写入真实掌机。阶段二的真机验收仍需：实际核心及配置核对、有效 CHD／CUE M3U 冷启动、换盘、游戏内存档延续、双存储映射与中断恢复。阶段 3A 再实现 CHD 能力检查、空间分析、本地转换与内容验证。
